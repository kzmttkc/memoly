## (G) セッション/テナント汚染の検証（Loop1の「環境異常」を実測で切り分け・重要）

Loop1 persona_05 は「他ペルソナの会社（つばさ介護センター）が表示される／セッションが上書きされる」現象を観測し、**原因を『同一ブラウザ/localStorage の並行共有』と推定**していた。Loop2 は**完全独立の new_context（Cookie/localStorage分離）**で監査したにもかかわらず、**同じ現象を再現**した:

- 登録直後に取得したセッション（`state.json`）で /company/billing・/company/account を開くと、サイドバーの「対象」会社が自分の `NPOみらい支援ネット` ではなく、**別の並行ペルソナ監査が作った `Formosa Ops KK (台湾系テスト)` に化けていた**。billing は「この会社の課金情報を表示する権限がありません」を返した。
- 認証済み API `GET /api/company`（自分のセッションCookie）は、自分が作った会社ではなく **`{"companies":[{"companyId":"3bbb78be…","name":"Formosa Ops KK (台湾系テスト)"…}]}` を返した**（他テナントの会社が自分のセッションに紐づく）。

**切り分け（実測で確定した事実）**:
- ブラウザは完全独立コンテキスト。よって**この汚染はブラウザ/localStorage層ではなく、サーバ/セッション発行層で起きている**（Loop1 の推定原因は誤り）。
- ただし**新しいコンテキストで /login し直すと、`GET /api/company` は自分の会社 `b09d7184 / NPOみらい支援ネット` のみを正しく返した**。すなわち定常状態（クリーンな単一ログイン）ではテナント分離は保たれている。汚染は**並行して多数のサインアップ/ログインが走る負荷下で、サインアップ発行時のセッションが別テナントに一時的に解決された**もの。
- **確信度**: 「独立ブラウザでも再現＝ブラウザ層でない」は実測で断定可（証拠: `/api/company` の生レスポンス）。一方「一般ユーザーの単独利用でも起きるか」は**未確認**。今回は複数のペルソナ監査を同一バックエンドに同時実行していたため、実運用の単独ユーザーでは再現しない可能性が高い。ただし**サインアップ直後のセッションが他テナントに解決され得る**という事実自体は、負荷やアカウント作成の同時実行が起こり得る本番で無視できないリスク。

**推奨**: サインアップ時のセッション発行と「アクティブ会社」解決を、確実にそのユーザーの userId にスコープする（同時サインアップのレースで別ユーザーの会社に解決されないか回帰テスト）。削除・課金など破壊的/金銭的操作の直前は、サーバ側でも `session.userId` と対象 `companyId` の所有関係を再検証すること（今回はクライアント側 guard で誤削除を防いだが、本来はサーバが最後の砦）。
